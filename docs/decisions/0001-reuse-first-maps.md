# Reuse-First Maps

Status: selected for the proposed roadmap by Parker's 2026-10-28 annotations; protected-branch integration awaits independent review. This selects an investigation method, not an engine or deployment.

## Context

The project aims for Google Maps-depth usefulness. Its first 34 tasks emphasize the desktop slice and device qualification; broad product/data work needs visible entry points. Parker approved a one-region desktop comparison and owning the integration first. He requested the sovereignty definition on the README, emphasized transparent components and repairable weak links, allowed broad contribution intake, and supplied the 29-candidate/16-packet handoff.

## Selected Approach

Compare CoMaps and GNOME Maps for a useful application path while independently investigating a bounded regional MOTIS service. Retain the existing trip/location/pack/platform seams and all original task IDs. Move transit discovery from P3 to P0; keep its DATA-01 provider gate. Record the maintainer-directed documentation scope under DATA-01 — Choose sustainable providers for the pilot, the existing trusted task for this source-discovery submission. New task IDs cannot authorize their own introduction. Add the 16 unclaimed proposal packets to the existing registry without new phase/state values or assigned humans.

Permit places, imagery, traffic-source and accessibility research early. Their runtime integration remains a scoped continuation. Define task dependencies around required outputs rather than library categories: tile delivery needs the chosen pack contract; scheduled transit needs feed discovery and the service result; realtime needs static schedules; private sync needs the existing handoff/privacy work. Source feasibility does not require a phone or a completed production service.

Open intake has no fixed task-count or founder-attention cap. Agents recommend include/scuttle/rebuild/reject; existing protected branches, independent human reviews and checks control integration. Individual contributors and operational experiments retain accepted resource limits.

## Alternatives

Assembling MapLibre, Photon, Valhalla and OTP immediately would create several maintenance obligations before a workflow shows the need. Keeping only a desktop/device roadmap would obscure the intended product depth. Promoting every handoff dependency literally would delay source research behind implementations it does not need. A permanent fork would assume an upstream integration gap that has not been demonstrated.

## Reopen the Choice When

Reconsider the application path if both clients fail an accepted workflow or cannot meet the data/privacy boundary. Add a specialist engine if the same fixture exposes an integrated-service gap and the measured benefit covers its operating cost. Select a different pilot if the region lacks permitted current inputs or a usable independent acceptance case. Fork only when the gap and a maintenance owner are established.

No field evidence, current feed validity, operating budget, accepted reviewer or supported device is established by this decision.
